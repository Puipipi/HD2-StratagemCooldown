# 战备冷却 / Stratagem Cooldown — 踩坑与解决记录

日期：2026-10-04 ｜ 版本跨度：2.2.2 → 4.1.0 ｜ 全部条目均为当天真实发生并复现过的问题

---

## 1. 模组管理器与打包

| 坑 | 症状 | 解决 |
| --- | --- | --- |
| 子选项使用空 `Include: [""]` 充当“纯界面项” | 管理器里整棵选项树**不显示** | 照能正常显示的模组（Cremator、Helmet Headlamp）的做法：插件根放 `Addon/` + `manifest.json`，**每个子选项的 `Include` 指向真实存在且含 payload 的目录**（2.8.0） |
| 子选项里的 payload 写成纯文本 Lua | 带上去就崩 / 黑屏 | 用与核心相同的 `build_addon()` **正规封装**，并在打包自检里比对每个子选项 payload 的首字节与核心信封是否一致（2.9.7） |
| 管理器导入时会**全勾**，而读取器取每个块的第一项 | 「关闭」排在第一 → 导入后**什么都不改**（日志：`red=false blue=false green=false`） | 六块全关闭时回退到内置配置（3.2.0）；随后改为**管理器零配置**、设置全部放游戏内页面（3.3.0） |
| 管理器库里的旧包（2.9.6）与手工放入的新层并存 | 在管理器里点“部署”会用旧包覆盖新层 | 要么先重新导入新包再部署，要么只使用已放好的层 |

## 2. 游戏内 Mod Options Menu（当天最大的坑）

| 坑 | 症状 | 解决 |
| --- | --- | --- |
| 使用了 `type='slider'` —— 该框架只支持 `toggle` 与 `choice` | 7 项只注册成功 2 项，页面上只有「绿战备」和「无限制」两个开关 | 以能正常工作的 **ExoLoadout v0.8.0** 为契约重写：`choice` 的 **`default` 必须是序号（数字）**，`host.get()` 也返回序号（3.0.0） |
| `choice` 的选项列表**上限 16 项** | 日志：`refused: percent (choice): choices must list 2 to 16 names`，超限的行整行消失 | 列表缩短：次数 7 档（不添加/+1..+5/无限制）、飞鹰 6 档（+1..+5）；百分比改为滑条（3.4.0 / 3.5.0 / 4.1.0） |
| **`mom_rescan` 的实现**在 3.0.0 重写菜单块时被删除，只剩调用点 | 游戏内改任何值**都不生效**；“每 10 秒重新写入”从未真正运行 —— 这是“改了没用/不生效”的真正原因 | 补回定义（3.7.0）。修复后离线可见：100% → 780、25% → 195、无限制 → -1 |
| 多个控件写同一个设置（百分比既有选择又有滑条实验项） | 互相覆盖，最后一个被点的生效 | **单一主人规则**：第一个注册成功的滑条行取得所有权，其余行不生效并在日志写明原因；滑条被拒时自动注册 3 档选择兜底（4.0.1 / 4.1.0） |

## 3. 生效机制与配置解析

| 坑 | 症状 | 解决 |
| --- | --- | --- |
| 曾推测“游戏会把值刷回原样” | 方向完全错误，浪费了排查时间 | **读旧版本 2.2.2 的源码注释**才发现：写入确实落在 `+0x68`，但游戏不读这个字段；让 2.2.2 生效的是**把与该值相同的镜像字段一起写**。教训：先读历史版本的注释与日志，不要凭空推断 |
| 中文取值解析失败（`仅载具`、`仅支援武器`、`全部` 等） | 配置写了等于没写（生成了 `仅vehicles` 这类无效值） | 别名表补齐新词并保持**最长优先**（2.9.5）；同时注意**分节与平铺两套解析器都要改**，只改一处会被另一处覆盖（2.9.6） |
| `in_scope()` 把未知家族（包括 `nil`）一律排除 | 未来更新新增的战备不会被修改 | 未知家族改为跟随红/蓝/绿开关（3.8.0） |
| Lua 作用域陷阱：函数在其定义之前被调用 | “重新扫描”类调用解析到 `nil`，静默失效（3.0.0 → 3.7.0 的全部症状） | 对这类函数做**前向声明**（`local f` 提前声明，定义处改为赋值）；对调用点加 `type(f)=='function'` 守卫 |

## 4. 启动与验证流程

| 坑 | 症状 | 解决 |
| --- | --- | --- |
| 进程检测写成大写 `Helldivers2.exe`，而 `tasklist` 的 `/FI` 过滤器**区分大小写** | 四次误判“游戏没启动”，白白多绕几轮 | 改为小写检测；启动改用 **Steam `-applaunch`**。另：直接运行游戏 exe 会留下 92 MB 的 Steam DRM 桩空转，那就是当时看到的“黑屏/崩溃” |
| 自己的检查脚本有过 bug（过滤 `.patch_0`，而部署文件名为 `.patch_323`） | 误报“游戏目录里 0 个层”，一度怀疑部署 | 改为按内容匹配 + **逐字节 sha256 比对**，确认部署无误 |
| 仓库单元测试断言了已经废弃的行为（“把百分比吸附到 100/80/50”，而该行为早已按要求移除） | 测试失败但产品行为正确 | 改为断言“自由数值原样使用 + 越界钳制” |

## 6. 流程教训

1. 先读**能正常工作的模组**再动手 —— ExoLoadout 一次就把框架契约钉死了。
2. 不要用自己写的假宿主作为验收标准；它只能验证逻辑，不能证明游戏行为。
3. 日志原文优先于推断；“已修好”必须附数值证据（例如 `780 → 273`）。
4. 版本一路堆到 4.1.0 会让人迷失 —— 之后只维护**一个包**、一次只走一条路。
5. 用户报告的现象要先复现再解释；“调不了/选项不全”这类描述背后往往是框架的一条硬规则。
